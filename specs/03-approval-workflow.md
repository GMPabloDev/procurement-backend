## Contexto

La SPEC 01 implementó identidades, roles, Approval Authority, scopes y `IOrganizationEligibilityService`, que devuelve candidatos con `EligibilityEvidence` pero no selecciona personas ni crea tareas. Los dominios transaccionales y la SPEC 02 necesitan una frontera que conserve requirements por target, aplique dependencias, impida autoaprobación y produzca resultados durables sin mutar documentos ajenos.

El borrador anterior de la SPEC 03 mezclaba ese núcleo con delegaciones, evolución de versiones, operación avanzada y el adapter completo de Policy. Esta revisión conserva el número 03 para el primer entregable verificable. La delegación y evolución quedan en SPEC 04; la integración con Policy y quotation waiver, en SPEC 05.

## Alcance

### Incluye

- Ingreso idempotente de casos y requirements desde adapters internos registrados y workloads allowlisted.
- Scopes tipados, targets versionados, dependencias entre approvals y prerrequisitos externos.
- Asignación automática al candidato elegible con menor carga, estado `UNASSIGNED` y reconciliación ante pérdida de elegibilidad.
- Exclusiones inmutables de Segregation of Duties y separación estricta de `ADMIN`/`AUDITOR` respecto de la candidatura, el assignment y la decisión empresarial.
- Acciones `APPROVE`, `REJECT` y `REQUEST_CHANGES` con revalidación de autoridad, concurrencia e idempotencia.
- Bandeja mínima del assignee, estado del caso para su originador o workload propietario y lectura organizacional de auditoría.
- Persistencia SQL Server, evidencia canónica, audit append-only y outbox de resultados por target.
- Cancelación de casos abiertos por el workload propietario, errores, límites, health y pruebas del núcleo.

### No incluye

- Delegaciones, vacaciones, activación programada o reasignación causada por una delegación; pertenecen a SPEC 04.
- Nueva versión de un caso, supersesión o carry-forward de decisiones; pertenecen a SPEC 04.
- Revocación de evidencia ya emitida y vistas operativas avanzadas; pertenecen a SPEC 04.
- Adapter de controles de SPEC 02, secuencia específica Department/Finance/Procurement o quotation waiver; pertenecen a SPEC 05.
- Purchase Requests, Cost Centers, budgets, proveedores, sourcing, POs, invoices, matching o payments.
- Quórums, votación, grupos, selección manual de assignee, escalamiento por SLA o notificaciones externas.
- Diseñador visual, scripts, expresiones arbitrarias, interfaz frontend o mutaciones sobre documentos origen.

## Comportamiento esperado

- **REQ-01 — Ingreso confiable e idempotente.** Un adapter in-process registrado exactamente una vez por `subject_type + operation + contract_version`, invocado por un workload autenticado y allowlisted, puede abrir un `ApprovalCase` para una organización y versión inmutable de sujeto. El comando incluye `submission_key`, referencia y digest del snapshot origen, `requester_id` cuando exista, `originator_id`, exclusiones SoD, requirements y prerrequisitos completos. La key es única en `(organization_id, workload_issuer, workload_client_id, subject_type, operation)`; repetir el mismo fingerprint devuelve el mismo caso sin resolver ni crear de nuevo y reutilizar la key con otro contenido devuelve `409`. Un caller HTTP de usuario no puede autocertificar requirements, scopes, exclusiones ni digests.

- **REQ-02 — Requirements, scopes y targets conservados.** Cada `ApprovalRequirement` contiene key estable, tipo, `stage_code`, rol, authority, `DecisionScopeDescriptor`, acciones, dependencias, exclusiones y targets. El descriptor usa JSON `decision-scope/v1` con propiedades exactas `{schema_version, organization_id, scopes}`; cada scope contiene `{dimension, reference_id, reference_version}`. `ORGANIZATION` exige referencias nulas y no se combina; `LEGAL_ENTITY` y `DEPARTMENT` exigen UUID y versión positiva activos. `COST_CENTER` permanece rechazado hasta que su catálogo extienda SPEC 01. Cada target usa `{type,id,version,material_snapshot_digest}` y todo requirement contiene al menos uno. Un requirement agrupa targets solo si descriptor, dependencias, acciones, decisión y exclusiones son idénticos; conserva `source_requirement_key` y una `workflow_requirement_key` estable y única dentro del caso.

- **REQ-03 — Grafo y prerrequisitos externos.** Las dependencias forman un DAG dentro del mismo caso. Cada edge declara predecessor `APPROVAL|EXTERNAL`, key, modo `ALL` y un conjunto no vacío de targets completos que pertenece a ambos nodos. Solo se satisface cuando todos esos targets están `APPROVED` o `SATISFIED`; coincidencias parciales o de otra versión/digest no habilitan tareas. Un `ExternalPrerequisite` conserva key estable y única dentro del caso, owner adapter/version, owner workload `issuer + client_id`, source control/digest, parámetros tipados, al menos un target y estado `WAITING|SATISFIED|FAILED|CANCELLED`. En el ingreso, un registro confiable resuelve cada combinación owner adapter/version a exactamente un workload allowlisted y persiste esa identidad; ausencia o ambigüedad devuelve `503` antes de crear el caso. Solo el workload autenticado que coincide exactamente en `issuer + client_id` puede cambiar `WAITING` a `SATISFIED|FAILED` mediante `signal_key`, fingerprint y versión esperada; compartir `client_id`, issuer o adapter id parcialmente no basta y devuelve `403`. `FAILED` es inmutable y bloquea los descendientes afectados; corregirlo exige un caso nuevo de SPEC 04.

- **REQ-04 — Asignación determinista y ausencia de candidato.** Al habilitar un requirement, el workflow convierte `DecisionScopeDescriptor` a `AuthorizationScopeSet` e invoca `IOrganizationEligibilityService` con rol, authority, scope, instante UTC y exclusiones exactas. Entre candidatos directos elige menor número de tareas actuales `PENDING` en la organización y desempata por UUID canónico ascendente. Selección, reserva de carga y assignment se serializan. Si no hay candidato, la única tarea actual queda `UNASSIGNED` y el caso `BLOCKED`, sin fallback. Cada cambio confirmado de perfil, rol, grant o scope solicita una sola corrida de reconciliación por su `AdministrativeAuditRecord`; una solicitud administrativa usa `reconciliation_key`. La corrida reasigna una tarea `PENDING` inválida o la devuelve a `UNASSIGNED`; una decisión terminal no cambia.

- **REQ-05 — Segregation of Duties fail-closed.** El contrato versionado del adapter declara actores obligatorios por operación y construye exclusiones inmutables. Toda aprobación empresarial exige `originator_id`; si existe un requester distinto, también se excluye. Un actor excluido no puede ser candidato, assignee ni decisor. Además, un usuario que en el instante evaluado tenga cualquier assignment local activo y ya efectivo de `ADMIN` o `AUDITOR` en la organización del caso queda excluido de candidatura, assignment y nuevas decisiones, con independencia del scope de ese assignment y aunque acumule el rol empresarial y la authority requeridos. Esta exclusión dinámica se consulta en la fuente de verdad al asignar, reconciliar y decidir; conceder uno de esos roles a un assignee invalida su assignment empresarial y dispara reconciliación. Campo obligatorio ausente, identidad vacía o exclusiones incompatibles con el adapter version se rechazan antes de persistir. Replay o reconciliación no pueden reducir ninguna exclusión.

- **REQ-06 — Decisión autorizada e inmutable.** Solo el assignee actual, activo y autenticado puede ejecutar `APPROVE`, `REJECT` o `REQUEST_CHANGES` sobre una tarea `PENDING`. Exige motivo no vacío, versión esperada y `decision_key`, única en `(organization_id, actor_user_id, decision_key)`. Antes de confirmar se vuelve a resolver elegibilidad y la exclusión de roles reservados de REQ-05 con la fuente de verdad y el reloj del servidor; un assignee convertido en `ADMIN` o `AUDITOR` recibe `403` sin crear decisión, audit de éxito ni outbox. Replay con fingerprint idéntico devuelve la decisión original aunque la tarea ya sea terminal o el actor haya adquirido después un rol reservado, porque no crea una decisión nueva; otra carga o una carrera incompatible devuelve `409`. Acción, targets, actor, UTC, motivo y `EligibilityEvidence` fresca son append-only.

- **REQ-07 — Estados, propagación y cancelación.** `ApprovalCase` transita `OPEN → BLOCKED|COMPLETED|CANCELLED`; un bloqueo por `UNASSIGNED` puede volver a `OPEN`, mientras un prerequisite `FAILED` solo permite cancelación hasta SPEC 04. Un requirement transita `WAITING → UNASSIGNED → PENDING → APPROVED|REJECTED|CHANGES_REQUESTED`, y cualquier estado no terminal puede terminar `CANCELLED`; la task refleja desde `UNASSIGNED` y no reabre. `APPROVE` habilita edges de sus targets; `REJECT` y `REQUEST_CHANGES` cancelan solo los requirements descendientes enlazados que aún no sean terminales, junto con sus tasks, y no alteran prerequisites ni otras entidades. El caso completa cuando todos los requirements vigentes son terminales y todo prerequisite está `SATISFIED`; un prerequisite `FAILED` lo mantiene bloqueado y solo puede cancelarse el caso. Un prerequisite `CANCELLED` únicamente existe cuando el caso ya fue cancelado por su workload propietario. Solo ese workload puede cancelar un caso no terminal —`OPEN` o `BLOCKED`, incluido el bloqueo por `FAILED`— con motivo y versión esperada: pasan a `CANCELLED` únicamente los requirements no terminales y los `ExternalPrerequisite` que estén `WAITING`; estados ya terminales permanecen intactos. La cancelación no borra decisiones, no reetiqueta targets ya terminales ni compensa efectos consumidos.

- **REQ-08 — Evidencia canónica y durable.** `approval-canonical-json/v2` serializa UTF-8 sin BOM ni whitespace, propiedades conocidas presentes y ordenadas ordinalmente, strings NFC, UUID `D` minúsculo, timestamps UTC con siete decimales, enums en mayúsculas, decimales invariantes y sets ordenados por bytes canónicos sin duplicados. Conserva preimages de `submission_fingerprint`, `decision_fingerprint`, `signal_fingerprint`, `authority_evidence_digest` y `workflow_decision_digest`. El digest de decisión liga caso/sujeto/snapshot, requirement/descriptor, targets, acción, actor, motivo, instante, exclusiones y evidencia de elegibilidad. Cada transición observable crea audit en su misma transacción. El actor es una unión cerrada y mutuamente excluyente: `USER` conserva `actor_user_id` UUID; `WORKLOAD`, `actor_workload_issuer + actor_workload_client_id`; y `SYSTEM`, `actor_system_id=APPROVAL_WORKFLOW`; los campos de las otras variantes son nulos y nunca se usa un UUID vacío. El audit raíz de submission, señal, cancelación o decisión conserva al `USER` o `WORKLOAD` autenticado y `caused_by=null`. Assignment inicial, activación, propagación, reasignación y liberación a `UNASSIGNED` son efectos automáticos: usan `SYSTEM` y apuntan mediante `caused_by={audit_stream:APPROVAL,audit_id:<root_audit_id>}` al audit raíz de la operación que los produjo. Toda corrida de reconciliación conserva exactamente un `root_audit_id`: una solicitud administrativa crea un raíz `USER` sin causa; una corrida solicitada por un cambio organizacional crea un raíz `SYSTEM` con `caused_by={audit_stream:ORGANIZATION,audit_id:<administrative_audit_id>}`. Los cambios de case/task de la corrida siempre usan `SYSTEM` y apuntan al `root_audit_id` `APPROVAL`. Un reclaim tras timeout o restart reutiliza la misma corrida, raíz y causa; nunca crea una raíz nueva. Cada efecto automático lleva un `automatic_effect_key` SHA-256 único para esa transición, causa y entidad fuente que cambia (`APPROVAL_REQUIREMENT`, `EXTERNAL_PREREQUISITE` o `APPROVAL_CASE`). Raíz, enlace causal y efecto se confirman según las fronteras transaccionales de Datos y contratos, no se infieren de `correlation_reference`; un replay sin nueva transición reutiliza la evidencia original sin duplicarla. Una transición produce resultado solo cuando (a) una decisión lleva un requirement a `APPROVED`, `REJECTED` o `CHANGES_REQUESTED`; (b) una señal lleva un `ExternalPrerequisite` desde `WAITING` a `SATISFIED` o `FAILED`; o (c) la propagación de un rechazo lleva requirements descendientes no terminales a `CANCELLED`, o la cancelación del caso lleva requirements no terminales y prerequisites `WAITING` a `CANCELLED`. Cada una crea exactamente un `ApprovalOutboxEvent` `approval-result/v2` por target de la entidad que realmente transitó y con ese resultado en la misma transacción. Su payload canónico contiene `result_source` con propiedades exactas `{type,id,key}`: `type` es `APPROVAL_REQUIREMENT` y `key` es `workflow_requirement_key`, o `type` es `EXTERNAL_PREREQUISITE` y `key` es la key estable del prerequisite; `id` siempre es el UUID no vacío de esa entidad. `decision_id` y `decision_digest` son no nulos únicamente para resultados `APPROVED`, `REJECTED` o `CHANGES_REQUESTED`; `decision_digest` transporta exactamente el `workflow_decision_digest` persistido de la `ApprovalDecision`, nunca el `decision_fingerprint`; ambos son nulos para `CANCELLED`, `SATISFIED` y `FAILED`. A efectos de eventos, un target es terminal para un requirement cuando ese requirement ya es terminal y para un prerequisite cuando ya no está `WAITING`; una entidad terminal no vuelve a emitir `CANCELLED`. Si el mismo target pertenece a varias entidades que transitan independientemente, cada transición conserva su propio evento y `result_source`. Ingreso, activación, assignment, reasignación, liberación a `UNASSIGNED` y cambios reflejados solo en case/task generan audit y la telemetría de NFR-05, pero no un evento de resultados adicional.

- **REQ-09 — API, visibilidad, errores y límites.** Un usuario activo consulta sus tareas `PENDING` y su historia de decisiones; el originador o workload propietario consulta su caso; `AUDITOR` organizacional lee casos, assignments, decisiones y evidencia dentro de su scope; `ADMIN` consulta `UNASSIGNED`, estado operativo del outbox y health, y solicita reconciliación con `reconciliation_key` o replay de dead letters. Esos permisos de rol no son intercambiables: `ADMIN` por sí solo no obtiene las lecturas organizacionales de evidencia reservadas a `AUDITOR`, y `AUDITOR` no ejecuta operaciones administrativas; un usuario con ambos assignments acumula solo esas capacidades explícitas. Esta separación no revoca la visibilidad que el mismo actor tenga por otra causa expresa —su bandeja o historia, ser originador o actuar como workload propietario—, siempre limitada al recurso correspondiente. Ninguno puede ser candidato, assignee ni decisor empresarial. Fuera del alcance visible se responde `404`. Se usan Problem Details: `401`, `403`, `404`, `400`, `409`, `413`, `422` y `503 /problems/approval-dependency-unavailable`. Un caso admite hasta 2.000 requirements, 10.000 vínculos entidad→target y 5 MiB canónicos. El límite de 10.000 es la suma de `requirement.targets.Count + prerequisite.targets.Count`: el mismo target en dos entidades cuenta dos veces, duplicarlo dentro de una entidad se rechaza y las apariciones en edges no cuentan. Keys y códigos usan los límites y alfabetos declarados en Datos y contratos.

- **REQ-10 — Exactly-one bajo concurrencia y operación segura.** Existe como máximo una task actual por requirement y como máximo una asociación de `ApprovalDecision` por `(requirement_id, target completo)`. Esa asociación existe exactamente una vez si el requirement termina por `APPROVE`, `REJECT` o `REQUEST_CHANGES`; si termina `CANCELLED`, existen cero asociaciones y no se crea una decisión sintética. La finalización por cancelación queda representada por estado, audit y el resultado `CANCELLED` de REQ-08. Ingreso, assignment, decisión, señal y cancelación usan índices y transacciones multiinstancia. Reconciliación usa `ApprovalReconciliationRun`, lease persistente de 30 segundos, renovación al menos cada 10 segundos y fencing token; solo el holder vigente confirma un checkpoint o efecto. Un lease expirado permite reclamar la misma corrida y continuar desde su cursor sin duplicar raíz, audit ni cambio. Outbox entrega al menos una vez con `event_id + contract_version`; reintenta a 1 s, 5 s, 30 s, 2 min y 10 min hasta 10 intentos, conserva `DEAD_LETTER` y permite replay administrativo sin editar payload. Health degrada si el evento pendiente más antiguo supera 5 minutos, una corrida debida no completa en 60 segundos o existe dead letter. Tras timeout el caller debe reintentar con su key.

## Datos y contratos

| Elemento | Datos mínimos | Regla o compatibilidad |
| --- | --- | --- |
| `ApprovalCase` | organización, subject type/id/version, operation, snapshot digest, workload, key/fingerprint, estado, versión | No contiene el documento origen; estados de REQ-07. |
| `DecisionScopeDescriptor` | schema version, organización, scopes tipados/versionados | Contrato exacto `decision-scope/v1`; referencias validadas contra SPEC 01. |
| `ApprovalRequirement` | source/workflow key, tipo, stage, role, authority, descriptor, exclusiones, dependencias, targets, estado | Keys únicas dentro del caso, uno o más targets indivisibles y máximo una task actual. |
| `ExternalPrerequisite` | key, owner adapter/version, owner workload issuer/client id, control/digest, parámetros, targets, estado, signal key/fingerprint, versión | Key única dentro del caso y uno o más targets; solo la identidad owner exacta señala. `FAILED` no se reabre; `CANCELLED` solo por cancelación del caso. |
| `ApprovalTarget` | type, id, version, material snapshot digest | Identidad completa usada por edges, decisiones y eventos. |
| `ApprovalTask` | requirement, targets, estado, assignment actual, versión | `UNASSIGNED`, `PENDING` y terminales de REQ-07. |
| `ApprovalAssignment` | task, assignee, UTC de alta/baja, carga, eligibility evidence, causa | Append-only; uno actual por task. |
| `ApprovalDecision` | task/requirement, targets, action, actor, reason, UTC, key/fingerprint, evidence, digests | Append-only; origen `HUMAN` en esta spec. |
| `ApprovalOutboxEvent` | id, contract version, caso/sujeto, `result_source {type,id,key}`, target, resultado, decisión/digest nullable, attempts/state | Contrato `approval-result/v2`; un evento por target y entidad fuente para `APPROVED`, `REJECTED`, `CHANGES_REQUESTED`, `CANCELLED`, `SATISFIED` o `FAILED`. `result_source`, la nulabilidad de decisión y el significado de `decision_digest=workflow_decision_digest` cumplen REQ-08; no representa submission, assignment ni lifecycle sin resultado. Consumer deduplica por `event_id + contract_version`. |
| `ApprovalAuditRecord` | actor type; actor user id, workload issuer/client id o system id nullables; `caused_by {audit_stream,audit_id}` nullable; `automatic_effect_key` nullable; UTC, acción, objetivo/versiones, scope, motivo, before/after, correlation | Append-only y minimizado. Exactamente una variante `USER`, `WORKLOAD` o `SYSTEM` está completa. `SYSTEM` usa `APPROVAL_WORKFLOW`; todo efecto automático sobre case/task exige raíz `APPROVAL`, `caused_by` y effect key únicos por entidad fuente. |
| `ApprovalReconciliationRun` | id, organización, trigger, trigger audit o admin key, estado, requested/started/completed UTC, cursor, lease owner/until/fencing token, attempts/last error, root audit id, versión | Estados `PENDING`, `RUNNING` o `COMPLETED`. Una corrida por audit organizacional o key administrativa; reclaim reutiliza id/root/cursor. Solo lease vigente avanza cursor o completa. |

Reglas adicionales:

- `submission_key` y `decision_key` miden 1–128 caracteres `[A-Za-z0-9._:-]`; códigos miden 1–128 ASCII `[A-Z][A-Z0-9_.:-]*`; motivos, 1–1.000 Unicode scalars.
- `signal_key` es única en `(organization_id, external_prerequisite_id, key)` y cada reuse exige fingerprint idéntico.
- `source_requirement_key`, `workflow_requirement_key` y la key de `ExternalPrerequisite` cumplen los límites de key; cada clase de key es única dentro de su caso.
- La carga cuenta solo tasks `PENDING`; una task agrupada cuenta como una unidad y no se rebalancea por cambios posteriores de carga.
- La decisión agrupada no se divide; respuestas distintas requieren requirements distintos antes de decidir.
- `valid_from` es inclusivo y `valid_to` exclusivo cuando aparezcan en evidencia de authority.
- Adapters y eventos se versionan; una versión desconocida se rechaza fail-closed.
- En `approval-result/v2`, `result_source.type` y `result` deben formar una combinación válida: `APPROVAL_REQUIREMENT` admite `APPROVED|REJECTED|CHANGES_REQUESTED|CANCELLED`, y `EXTERNAL_PREREQUISITE` admite `SATISFIED|FAILED|CANCELLED`. `result_source.id` y `result_source.key` identifican la misma entidad persistida del caso y no pueden inferirse solo del target.
- Un audit raíz de comando directo tiene actor `USER|WORKLOAD`, `caused_by=null` y `automatic_effect_key=null`. Un efecto automático tiene actor `SYSTEM`, `caused_by` `APPROVAL` obligatorio hacia esa raíz y `automatic_effect_key` no nula. Solo la raíz `SYSTEM` de una corrida por cambio organizacional usa `caused_by` `ORGANIZATION`; la raíz de una corrida administrativa es `USER` sin causa. El destino causal debe existir al confirmar, pertenecer a la misma organización, no apuntarse a sí mismo y nunca modificarse.
- `automatic_effect_key` es SHA-256 de `approval-canonical-json/v2` sobre propiedades exactas `{action,actor_system_id,after_version,before_version,canonicalization_version,case_id,caused_by,effect_source,organization_id,target_id,target_type}`; valores nullable están presentes. `effect_source` usa propiedades exactas `{id,key,type}` y señala la entidad persistida cuya transición origina el efecto: `APPROVAL_REQUIREMENT` con `workflow_requirement_key`, `EXTERNAL_PREREQUISITE` con su key estable o `APPROVAL_CASE` con `key=null`. Es única en la organización y un retry con la misma key reutiliza el audit, mientras una preimage distinta es conflicto.
- `ApprovalReconciliationRun.trigger` es `ADMIN|ORGANIZATION_CHANGE`. `ADMIN` exige `reconciliation_key` de 1–128 caracteres y unicidad `(organization_id, actor_user_id, reconciliation_key)`; `ORGANIZATION_CHANGE` exige audit de SPEC 01 y unicidad `(organization_id, trigger_audit_id)`. Crear la corrida y su root audit objetivo `RECONCILIATION_RUN/<run_id>` es atómico y `root_audit_id` queda fijado antes de procesar casos. `requested_at` es el UTC del audit organizacional que la disparó o del root administrativo; `started_at` se fija solo en el primer claim y `completed_at` debe quedar dentro de los 60 segundos desde `requested_at`. Al reclamar `PENDING` o `RUNNING` con lease expirado, una actualización condicional fija un owner opaco de instancia de 1–120 caracteres, `locked_until=now+30s`, e incrementa fencing token y attempts. El holder renueva como máximo cada 10 segundos y cada transacción de caso comprueba owner, token y no expiración. Cursor y orden de casos usan UUID `D` ascendente. Un crash conserva `RUNNING`, cursor y root; el siguiente holder continúa la misma corrida. Completion limpia el lease, fija UTC y nunca se reabre; `last_error` se minimiza sin stack, payload ni PII.
- `correlation_reference` es un identificador opaco generado o proyectado por el servidor, de 1–120 caracteres ASCII `[A-Za-z0-9._:-]`; no acepta texto libre del usuario/workload y no se usa como identidad, idempotency key ni causa.

### Contratos canónicos de Approval

Todos los objetos siguientes usan propiedades exactas, presentes incluso cuando son `null`; agregar, quitar o reinterpretar una propiedad exige una nueva `canonicalization_version`. `requirements`, `prerequisites`, `actions`, `dependencies`, `exclusions` y `targets` son sets ordenados por bytes canónicos y rechazan duplicados. `parameters` contiene JSON tipado ya canónico, persistido como string sin reserialización.

| Documento o preimage | Propiedades exactas |
| --- | --- |
| `submission_fingerprint` | `adapter_id`, `adapter_version`, `canonicalization_version`, `operation`, `organization_id`, `originator_id`, `prerequisites`, `requester_id`, `requirements`, `source_snapshot_digest`, `subject_id`, `subject_type`, `subject_version`, `submission_key`, `workload_client_id`, `workload_issuer` |
| requirement de submission | `actions`, `authority`, `dependencies`, `exclusions`, `role`, `scope`, `source_requirement_key`, `stage_code`, `targets` |
| prerequisite de submission | `key`, `owner_adapter_id`, `owner_adapter_version`, `owner_workload_client_id`, `owner_workload_issuer`, `parameters`, `source_control_digest`, `source_control_type`, `targets` |
| `authority` | `amount_base`, `base_currency`, `kind`, `minimum_rank`, `type` |
| dependency | `mode`, `predecessor_key`, `predecessor_kind`, `targets` |
| target | `id`, `material_snapshot_digest`, `type`, `version` |

## Migración, despliegue y reversión

- La persistencia se añade bajo un schema explícito de Approval y no modifica tablas de Organization o Policy. Las referencias a dominios futuros son identidades/versiones tipadas, no FKs a tablas inexistentes.
- Se aplica primero la migración, luego la aplicación con resolver y adapters controlados y finalmente se habilitan submissions. Sin resolver o con registro de adapters ambiguo, el módulo falla cerrado.
- Dispatcher y reconciliador usan leases persistentes; tras restart recuperan trabajo pendiente. Solo `ADMIN` puede reintentar dead letters o reconciliaciones sin editar datos contractuales.
- `approval-result/v2` y `approval-canonical-json/v2` son las primeras versiones publicables de resultados y preimages; el único origen de upgrade soportado es la línea base integrada sin datos Approval v1. No se crean eventos ni digests nuevos v1, no hay dual-write y ningún payload/preimage v1 persistido se reetiqueta, reescribe ni reutiliza como v2. Antes de aplicar la migración o habilitar submissions/dispatcher v2, el preflight exige cero eventos v1 en cualquier estado. Un hallazgo bloquea el rollout: no existe consumer v1 autorizado ni recuperación automática; solo se reintenta desde una base limpia o restaurada al backup pre-Approval, sin editar ni despachar esas filas.
- SPEC 04 y SPEC 05 siguen en borrador y sus referencias actuales a canonicalización v1 son incompatibles; su propia revisión debe migrarlas explícitamente a v2 antes de aprobarlas o implementarlas.
- Revertir la aplicación conserva casos, tasks, decisiones, audit y outbox. No se autoriza migración descendente destructiva. Antes del primer tráfico v2 puede volver la aplicación previa conservando el schema vacío; después de persistir un resultado v2 no se vuelve a una versión incapaz de consumirlo: se deshabilitan submissions, se mantiene el dispatcher/consumer v2 y se corrige hacia adelante.
- Antes de tráfico se prueban caso simple, DAG, `UNASSIGNED`, decisión concurrente, cancelación, restart y replay.

## Seguridad y privacidad

- Usuarios usan JWT y autorización local de SPEC 01; claims empresariales del IdP no conceden tasks ni decisiones. Submissions, señales y cancelación exigen workload allowlisted. Prerequisites y audit ligan al workload por `issuer + client_id`; adapter id, client id o issuer aislados no autorizan. `APPROVAL_WORKFLOW` identifica al componente ejecutor, no es una credencial ni sustituye al actor causal; el enlace `caused_by` impide atribuir al assignee o al caller una selección automática.
- El decisor debe ser assignee actual y seguir siendo elegible en la transacción. Un assignment previo, Job Title o la posesión de un enlace no bastan; un assignment activo de `ADMIN` o `AUDITOR` impide la candidatura y toda decisión nueva aunque el usuario tenga además el rol empresarial y la authority necesarios.
- Exclusiones SoD forman parte del requirement y del digest, y no se reducen durante assignment, reconciliación o replay.
- Bandeja, respuestas y telemetría omiten tokens, subjects de IdP, snapshots completos, saldos, documentos y PII innecesaria.
- `ADMIN` restaura operación, pero no crea evidencia de authority, selecciona assignee, cambia decisiones terminales ni obtiene por ese rol las lecturas de evidencia de `AUDITOR`. `AUDITOR` nunca muta. Ninguno puede acumular esas funciones con la de candidato, assignee o decisor empresarial mientras su assignment reservado esté activo.

## Requisitos no funcionales

- **NFR-01 — Determinismo reproducible.** El mismo comando canónico, snapshot de elegibilidad/carga y reloj produce el mismo assignment, decisión, bytes y digests; un replay devuelve los artefactos originales.
- **NFR-02 — Atomicidad e inmutabilidad.** Cada transición, su audit y el enlace al audit causal se confirman o revierten juntos; cuando la transición produce un resultado de REQ-08, sus eventos por target se confirman o revierten en la misma transacción. Requirements, decisiones, assignments liberados y relaciones causales no se sobrescriben.
- **NFR-03 — Consistencia de autoridad.** Una decisión revalida estado confirmado y una revocación de rol/grant o la concesión de `ADMIN`/`AUDITOR` no se prolonga ni se omite mediante caché; una reconciliación debida ocurre en máximo 60 segundos y cada cambio producido referencia el audit raíz de su corrida.
- **NFR-04 — Disponibilidad segura.** Fallos de resolver, adapter, persistencia o ambigüedad nunca degradan a aprobación ni conservan silenciosamente un assignee inválido.
- **NFR-05 — Observabilidad minimizada.** Submissions, assignments, `UNASSIGNED`, decisiones, conflictos, reconciliación y dispatch emiten métricas, logs y trazas OpenTelemetry sin motivos completos, snapshots ni PII.

## Decisiones

- **DEC-01 — Núcleo genérico con adapters tipados.** El workflow no conoce estados internos de PR, Supplier, Invoice o Payment; cada dominio aporta subjects, requirements, exclusiones y proyección mediante contratos versionados.
- **DEC-02 — Menor carga con desempate estable.** Se elige entre candidatos directos válidos por tareas `PENDING` y UUID; se descartan bandeja compartida y selección manual.
- **DEC-03 — Elegibilidad en assignment y decisión.** Se conserva evidencia de ambos instantes; no se confía indefinidamente en el assignment.
- **DEC-04 — Dependencias explícitas, no diseñador.** Un DAG acotado enlaza approvals y controles externos; `stage_code` solo etiqueta.
- **DEC-05 — El dominio propietario proyecta estado.** El workflow emite resultados durables y no modifica documentos ajenos.
- **DEC-06 — División por entregables.** Esta spec entrega el núcleo; SPEC 04 añade delegación/evolución y SPEC 05 integra Policy/waiver para mantener contratos verificables y revisables por separado.
- **DEC-07 — Outbox reservado a resultados.** Audit registra todas las transiciones observables; el canal de resultados solo publica, por entidad que realmente transita y por target, el vocabulario cerrado de REQ-08. Se descarta inventar resultados para submission, assignment o lifecycle reflejado y reetiquetar como `CANCELLED` un target ya terminal.
- **DEC-08 — Separación estricta de funciones administrativas.** Un assignment activo de `ADMIN` o `AUDITOR` excluye al usuario de aprobación empresarial aunque acumule otros roles o grants. Se descarta interpretar cada rol de forma aislada porque permitiría administrar o auditar y decidir el mismo flujo.
- **DEC-09 — Fuente de resultado explícita en v2.** Cada evento publica una fuente tipada con UUID y key estable bajo `approval-result/v2`; se descarta inferirla de campos nulos o del target y se evita reinterpretar el payload provisional v1.
- **DEC-10 — Cancelar no es decidir.** Un requirement cancelado no crea `ApprovalDecision`; su estado, audit y evento `CANCELLED` conservan la causa sin inventar actor, authority ni digest de decisión.
- **DEC-11 — Workload owner con identidad completa.** Owner adapter/version se resuelve exact-one a un workload allowlisted y se persiste/audita como `issuer + client_id`; se descarta equiparar adapter id con client id porque no acredita al issuer.
- **DEC-12 — Ejecutor automático y causa separados.** Los cambios automáticos se atribuyen a `SYSTEM/APPROVAL_WORKFLOW` y enlazan un audit raíz inmutable. Se descarta heredar el caller como actor —no realizó la selección— y variar entre síncrono/worker porque volvería inestable la semántica histórica.
- **DEC-13 — Canonicalización v2 por cambio de preimage.** Añadir owner workload a submission, effect keys y el payload completo estabiliza `approval-canonical-json/v2`; se descarta reutilizar v1 porque el repositorio exige versionar todo cambio de preimage.
- **DEC-14 — Identidad de fuente en efectos y eventos.** `automatic_effect_key` identifica la entidad persistida que origina el efecto mediante `effect_source {type,id,key}` y `approval-result/v2.decision_digest` publica exactamente `workflow_decision_digest`; se descarta usar un `requirement_id` nullable sin variante porque colisiona con prerequisites sobre el mismo target, y se descarta publicar `decision_fingerprint` como digest de resultado porque solo prueba idempotencia del comando.

| Decisión con autoridad revocada | Un assignee decide tras perder role/grant/scope | Revalidación en transacción, reconciliación y CA-05. |
| Dependencia habilitada por target incorrecto | Coincide id pero no versión/digest | Referencia completa y CA-03. |
| Doble decisión o evento | Dos instancias confirman resultados incompatibles, dos prerequisites sobre el mismo target comparten key de efecto o un consumer interpreta `decision_digest` como fingerprint | Índices, rowversion, `effect_source`, `workflow_decision_digest` explícito y outbox deduplicable. |
| Fuente de resultado ambigua o payload v1 reetiquetado | Dos entidades sobre el mismo target son indistinguibles o cambia el significado de un evento persistido | `result_source` obligatorio en v2, validación cruzada, preflight desde línea base limpia y CA-06. |
| Workload suplanta al owner de un prerequisite | Coincide solo adapter id, client id o issuer y la señal se acepta o queda sin atribución | Binding exact-one, comparación `issuer + client_id`, audit tipado y CA-03. |
| Efecto automático mal atribuido o sin causa | El assignee figura como actor, un worker no tiene identidad o no puede seguirse el disparador | `SYSTEM/APPROVAL_WORKFLOW`, root/effect key y `caused_by` inmutable en CA-04/CA-06. |
| Reconciliación duplicada o stale | Dos workers avanzan una corrida, restart crea otra raíz o un lease vencido confirma | Run único, lease 30 s, renovación, fencing token, cursor y CA-04. |
| `ADMIN` o `AUDITOR` acumula decisión empresarial | Un rol reservado también aparece como candidato, assignee o decisor por tener otro rol/grant | Exclusión dinámica en assignment/reconciliación/decisión y CA-05/CA-08. |
| Exposición de datos sensibles | Bandeja o trazas incluyen documento o identidad innecesaria | Proyección mínima, allowlist y CA-08. |
